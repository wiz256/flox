⏺ Why It's Blazingly Fast

  Here's the breakdown of why 1,594 backtests across 12,000 bars completes in under 2 seconds:

  1. Zero-copy shared data (biggest win)

  static std::vector<BarEvent> g_bars;  // loaded ONCE, shared by ALL backtests
  The 12,000 bars are parsed from CSV once, then every thread reads them directly — no copying, no IPC, no serialization. Each thread just gets an index via
  nextIdx.fetch_add(1).

  2. Lock-free work stealing

  std::atomic<size_t> nextIdx{0};
  size_t i = nextIdx.fetch_add(1);  // O(1), no mutex, no contention
  No thread pool overhead, no task queue. Just a single atomic counter — each thread grabs the next combination and goes. This scales linearly with cores.

  3. Compact strategy state

  Each strategy holds only:
  - A few deque<double> (typically 20-200 elements)
  - A few streaming EMA/ATR/RSI objects (each ~32 bytes)

  Total per-strategy state: under 2 KB. Compare to Python where each strategy holds DataFrames with 12,000 rows × 6 columns = ~576 KB per indicator copy.

  4. O(1) per-bar indicator updates

  The streaming indicators are constant-time per bar:
  void update(double v) { _ema = (v - _ema) * _mult + _ema; }  // 3 FP ops
  Not recomputing SMA over the full window every bar. The EMA is literally one multiply-add. ATR is similar. RSI is 2 EMA updates + one division.

  5. No DataFrame overhead

  Python backtests (VectorBT, pandas) allocate and copy DataFrames for every combination. Here, we just iterate over g_bars in-place with a few double variables
  on the stack. No allocations in the hot loop.

  6. BacktestRunner::runBars() is a tight loop

  From the FLOX source, runBars() iterates BarEvent objects sequentially — no event bus, no disruptor, no async. Just:
  for (auto& bar : bars) { strategy.onBar(bar); }

  7. Compile-time optimization

  Built with -O3 -march=native -flto (Release mode). The compiler inlines all the streaming indicator methods, eliminating function call overhead entirely.

  To make your code this fast, the key principles are:

  1. Load data once, share read-only across all workers
  2. Streaming indicators — O(1) update, not batch recomputation

  5. Single-file strategies — no virtual dispatch overhead for indicators (CRTP or inline)
  6. Compile with -O3 -march=native
